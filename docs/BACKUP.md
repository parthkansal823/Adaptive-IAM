# Offline IAM backup and restore

`scripts/backup_state.py` saves the local IAM SQLite database, its OIDC RSA signing key and its factor-encryption key together. Keeping the same signing key preserves the provider's public signing identity (`kid`); the factor key preserves enrolled TOTP secrets, passkey user handles and context fingerprints. Optional `deployment.json` is retained as configuration metadata. SQLite sessions, application registrations, grants, audit history and synchronization outbox are included in the database snapshot.

The archive contains credentials and private keys in plaintext. SHA-256 checksums detect accidental corruption; they do not authenticate a backup against an attacker who can replace the archive and its manifest. Store backups outside the checkout in storage with restricted access, encryption at rest and an operator-defined retention policy. The output name must end in `.iam-backup.zip`, a Git-ignored credential archive suffix; no output path is chosen by default. Linux staging directories are created with mode `0700` and files with mode `0600`. Windows supplies a protected DACL at file/directory creation, granting full control only to the running account and SYSTEM; permissive parent ACLs are not inherited. These protections take effect before any secret bytes are written, and remain on the published archive/restored directory. Windows filesystems without persistent ACL support are refused. Filesystem administrators retain access. Do not commit or attach backups to issues.

Stop the API and every other IAM writer before either operation, including other worker processes or containers sharing its data volume. `--offline` acknowledges this requirement; the tool cannot establish that every process is stopped. The SQLite backup API captures committed WAL data, but cannot make database and key changes atomic while services are running. Backup uses a temporary private directory alongside the output and publishes the completed archive exclusively; an existing output is never replaced, including when another process creates it immediately before publication. The output filesystem must support hard links (for example NTFS or ext4). Use an operator-controlled parent directory so other accounts cannot rename or substitute path components during an operation.

From the repository root on Windows, using the configured virtual environment:

```powershell
# First stop npm run dev / the API and all other IAM writers.
.venv\Scripts\python.exe scripts/backup_state.py create --offline --data-dir backend/data --output D:/ProtectedBackups/iam-2026-10-21.iam-backup.zip

# Restore to a new path; the parent must already exist.
.venv\Scripts\python.exe scripts/backup_state.py restore --offline --archive D:/ProtectedBackups/iam-2026-10-21.iam-backup.zip --destination D:/ProtectedIAM/restored
$env:IAM_DATA_DIR = 'D:/ProtectedIAM/restored'
```

On Linux, substitute `.venv/bin/python` and suitable protected absolute paths. `--data-dir` defaults to `IAM_DATA_DIR`, then `backend/data`. Create the output parent in advance and ensure sufficient free space for an uncompressed staging copy plus the archive. The current archive format limits the database to 2 GiB.

If the factor key is outside the data directory, `create` reads `--factor-key-file`, then `IAM_FACTOR_KEY_FILE`, then `factor-encryption.key` in the data directory. The archive always uses the canonical filename `factor-encryption.key`. After restore, unset `IAM_FACTOR_KEY_FILE` so the restored default is used, or point it explicitly at the restored key. Keep the previous environment/configuration available securely: `.env`, issuer/frontend URLs, TLS configuration, trusted proxy settings, passkey RP/origin settings, model cache and relying-party website secrets/sessions are not included. Retain the original OIDC issuer and compatible frontend/passkey origins for existing integrations. Changing the signing key or issuer invalidates existing token verification assumptions.

Restore requires a destination that does not exist; even an empty directory is refused. Every archive entry must have an exact supported filename. Unknown entries, duplicate filenames/JSON fields, paths, links, unsupported entry types, oversized data, checksum mismatches and invalid keys are rejected. SQLite integrity, foreign-key consistency, required identity tables and manifest metadata are checked; encrypted enrolled/pending TOTP secrets must decrypt with the supplied factor key. Validation happens in a private sibling staging directory before atomic directory publication. Windows uses its non-replacing rename; Linux uses `renameat2(RENAME_NOREPLACE)`, preventing replacement even if a competing process creates an empty destination after validation. Linux requires a libc, kernel and filesystem supporting that operation; missing/unsupported support fails closed with no ordinary-rename fallback. Other operating systems are unsupported. Failed validation/installation removes only the original staging directory; successful publication never removes a newly created directory reusing its old temporary pathname. Abrupt process termination or power loss can leave a `.iam-backup-*` or `.iam-restore-*` directory in the protected parent; review and remove these private temporary artifacts while services are stopped. The command does not guarantee crash/power-loss durability of directory entries. Checksums and SQLite checks do not establish the correctness of authorization decisions or the audit chain's provenance.

Run the focused synthetic-state checks with `.venv\Scripts\python.exe scripts/run_tests.py -s scripts/tests -p test_backup_state.py` (or the Linux virtual-environment path). Windows tests inspect the actual protected DACLs before each output's first write and exercise atomic publication collisions. A Windows restricted-token sandbox can deny writes inside owner/SYSTEM-only directories even when the operator account owns them; run these checks as the intended ordinary operator account rather than weakening the backup ACLs. The suite also tests the Linux syscall flags and fail-closed error paths through simulated libc responses; an actual Linux recovery exercise is still required before relying on that platform.

This backs up local IAM state only. Ganache/Besu validator databases, chain signer credentials and external chain state are not backed up. With Web3 enabled, stop the associated stack and retain a consistent separate chain/volume backup and its configuration; restoring IAM alone against reset, newer or different chain state can deliberately deny access because checkpoints/grants differ. Follow [deployment operations](../deployment/README.md) and [Web3 network operations](WEB3_NETWORK.md). The tool never resets or bypasses those checks. Use a maintenance window and test a complete recovery before relying on it.

Before restarting, review the restored data path, factor key override, demo/private mode and external chain configuration. Start one API instance, check `/api/health`, sign in, inspect the audit verification view and complete an OIDC login plus a permitted/denied resource check. Existing token/session expiry times and revocation state are retained, so expired sessions remain expired; this is not a session-extension or credential-recovery mechanism. Secure deletion, scheduled backup rotation, off-host replication and production disaster recovery remain operator responsibilities.
