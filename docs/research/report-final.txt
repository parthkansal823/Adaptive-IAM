ABSTRACT

Traditional Identity and Access Management (IAM) systems rely heavily on static authentication and authorization mechanisms, which are increasingly ineffective against modern cybersecurity threats such as credential theft, insider attacks, and unauthorized data access. These systems often apply uniform security controls regardless of contextual risk, leading either to weakened security or unnecessary user friction. Moreover, centralized identity storage introduces single points of failure, reducing transparency and trust.
This project proposes an intelligent, adaptive, and decentralized IAM framework aligned with Zero Trust principles by integrating dynamic risk-based authentication, Large Language Models (LLMs), and blockchain technology. The system continuously evaluates contextual and behavioural parameters—including user behaviour, device characteristics, location, access time, and resource sensitivity—to compute real-time risk scores. Based on the assessed risk level, authentication strength is dynamically adjusted using adaptive multi-factor authentication (MFA). LLMs are employed to provide contextual reasoning for access decisions and to assist in intelligent approval workflows for sensitive or unauthorized access requests. Blockchain technology ensures tamper-resistant storage of identity proofs, access approvals, and audit logs, thereby enhancing transparency, integrity, and non-repudiation.
Experimental evaluation demonstrates that the proposed framework significantly improves access control adaptability, reduces administrative overhead, and strengthens security while maintaining a smooth user experience. The results indicate that combining AI-driven decision support with decentralized identity management offers a scalable and effective solution for next-generation IAM systems in modern digital environments.

CHAPTER 1
INTRODUCTION

Problem Definition
In today’s digital world, organizations heavily depend on technology, especially the Internet, to manage users, data, and resources. With the rapid increase in usage, the volume of data and services has grown significantly. Every modern system includes authentication and authorization mechanisms to ensure security and proper access control.
Authentication is the process of verifying a user's identity before granting access to resources. It ensures that the user is genuinely who they claim to be, using credentials such as usernames and passwords, biometrics, or one-time passwords (OTP). Authorization determines what actions a user is allowed to perform after authentication. It defines the permissions and access levels assigned to the user. Authorization always follows authentication.
However, most current authentication and authorization systems rely on predefined static rules. While these approaches work in simple environments, they struggle to adapt to changing user behaviour, varying risk levels, and modern security threats such as stolen credentials, insider threats, and unauthorized data access.
Current Identity and Access Management (IAM) systems often treat all users in the same way, apply identical authentication requirements regardless of the actual risk involved. This can either weaken security (if controls are too relaxed) or create unnecessary friction for users (if controls are too strict). Additionally, the process of granting or revoking access is often manual, time-consuming, and lacks transparency and accountability. Centralized storage of user data further introduces risks of creating a single point of failure, which can be exploited through data breaches or manipulation.
Static authorization models are also limited, as they cannot efficiently handle dynamic environments where user roles, contexts, and conditions frequently change. As a result, there is a clear need for an intelligent, adaptive, and secure access control system. Such a system should be capable of:
Evaluating user risk in real time
Dynamically adjusting authentication strength
Providing transparent and tamper-resistant identity management
Maintaining a smooth and trustworthy user experience
In conclusion, authentication and authorization remain essential components of secure systems, but modern challenges demand adaptive, risk-aware, and scalable solutions to ensure both security and usability.

Problem Overview 
As increasingly rely on digital systems, managing who can access data and which type of data and resources has become more critical than ever. Most existing access control systems are built on predefined rules that does not change according to user behaviour or risk. Thus, make ineffective against modern security threats such as stolen credentials, insider threats or unauthorized access.
Current IAM solutions apply the same security checks to every user, regardless of the situation. While this can make systems safer, it also frustrates legitimate users with unnecessary authentication steps. At the same time, approving access to sensitive information is often a slow and manual process, lacking transparency and clear accountability. Also, user identities are stored in centralized systems which increases the risk of large-scale data breaches.
Because of these limitations, there is a growing need for a smarter and more flexible access control approach. Thus, there should be an effective solution to understand context, assess risk dynamically, and apply appropriate security measures while ensuring transparency, trust, and a smooth user experience.

Task Identification
Based on the limitations of traditional authentication and authorization systems, the primary task is to design and develop an intelligent, adaptive, and secure system that overcomes the drawbacks of static rule-based approaches.
The system should be capable of analysing user behaviour, context, and risk levels in real time to make dynamic access decisions. Unlike conventional systems, it must not treat all users equally but instead adjust authentication mechanisms and access permissions based on the level of risk involved.
The key tasks involved in this system include:
Developing a dynamic authentication mechanism that can adapt (e.g., require OTP, biometric, or multi-factor authentication based on risk level).
Implementing risk-based authorization to control user access depending on behaviour, location, device, or activity patterns.
Ease access provisioning and revocation, reducing manual effort and improving efficiency.
Ensuring transparency and accountability by maintaining secure logs and audit trails of all access-related activities.
Reducing dependency on centralized systems by exploring secure and tamper-resistant approaches for identity management.
Enhancing overall security while maintaining a smooth and user-friendly experience.
The goal of this task is to build a Next-generation Identity and Access Management (N-IAM) system that is secure, scalable, adaptive, and capable of handling modern cybersecurity challenges effectively.

LITERATURE SURVEY

2.1 Literature survey
Adaptive, AI-driven authentication is a growing focus for securing sensitive data. Recent research emphasizes risk-based authentication (RBA), which dynamically adjusts login challenges by computing a risk score from user behavior and context[1][2]. For example, Wiefling et al. (2022) present a large-scale RBA study (3.3M users, 31M logins) and offer an open synthesized login dataset[3][4]. Picard and Pierre (2023) propose RLAuth, a deep-reinforcement-learning RBA system for mobile, achieving a 92.6% G-Mean on public smartphone data[2][5]. Fereidouni et al. (2024) introduce F-RBA, a federated-learning RBA framework that trains risk models locally on devices (preserving privacy) and outperforms conventional anomaly detectors in true-positive rate[6]. These efforts highlight a shift toward ML/FL-based, contextual, continuous authentication.
Behavioral and continuous authentication (e.g. via sensors or biometrics) is surveyed by Baig & Eskeland (2021), noting privacy–security trade-offs of passive user monitoring[7]. Such methods can complement RBA by continuously verifying identity during a session.
For trust/risk scoring, Wang et al. (2023) propose a zero-trust model (AU-ZTAC) that computes user trust scores for fine-grained IoV (vehicle) access control[8]. This demonstrates the use of attribute-based trust metrics to reflect user intent in access decisions.
On the blockchain side, several frameworks demonstrate immutable logging and decentralized access control. Hu et al. (2023) present “N-Accesses”, using Ethereum smart contracts to enforce limited (n-times) data access and audit logs[9]. Yaqub et al. (2024) describe a policy-based AC for healthcare, where smart contracts enforce consent and GDPR-compliant data sharing[10]. Tawfik et al. (2025) propose ACHealthChain (on Hyperledger Fabric and IPFS) with fine-grained “PolicyChain” and “LogChain” modules, greatly improving throughput and auditability over prior systems[11]. These show blockchain’s strengths in tamper-proof logging, distributed policy enforcement, and privacy-preserving data sharing.
Finally, human-in-the-loop governance is an emerging idea: e.g. flagging anomalous requests to a panel of stakeholders. No standard architecture exists yet, but analogous concepts appear in AI/ML governance literature (e.g. “oversight” to ensure trust), suggesting policy committees or DAO-style voting could be applied to sensitive access requests.
2.2 Research Gaps
We found few works combining RBA with blockchain or with human review. Specifically, there is little explanation for AI for access control or integrated human voting in an ML + blockchain authentication system. This gap suggests opportunity to design a transparent, auditable pipeline: ML risk-scoring + dynamic auth → blockchain log → (if needed) human committee vetting.

2.4 Research Paper Summaries
Wiefling et al. (2022) – “Pump Up Password Security!” (ACM Trans. on Privacy & Security)[3]. Large-scale empirical RBA study: 3.3M users, 31M logins over 1 year. Examines RBA configurations and ML optimization to balance security/usability, and even replaces IP with RTT for privacy. Key deliverables include an open synthesized login dataset and ML-tuned risk parameters[3][4]. Relevance: provides data & insights for building ML-driven risk scoring.
Picard & Pierre (2023) – “RLAuth: A Risk-Based Authentication System Using Reinforcement Learning” (IEEE Access)[2][5]. Proposes RLAuth: a mobile RBA system using deep reinforcement learning (DRL) for anomaly detection. The DRL agent dynamically selects authentication challenges (e.g. biometric vs PIN) based on context and data sensitivity. Introduces balanced sampling to handle class imbalance. Results: On the CRAWDAD Telefonica MobilePhoneUse dataset (42 users, ~0.9M samples), RLAuth achieves 92.6% G-mean, outperforming standard classifiers[2]. Relevance: shows ML (RL) can drive adaptive auth and continuous verification on smartphones.
Fereidouni et al. (2024) – “F-RBA: A Federated Learning-based Framework for Risk-based Authentication” (arXiv)[6]. Introduces F-RBA, which trains RBA models via federated learning, keeping user data on-device for privacy. Novelty: a similarity-based feature engineering for heterogeneous data. Results: On a real-world multi-user login dataset, F-RBA yields higher true-positive rates for detecting suspicious logins than traditional unsupervised methods[6]. Relevance: federated approach informs privacy-preserving ML for risk scoring.
Baig & Eskeland (2021) – “Security, Privacy, and Usability in Continuous Authentication: A Survey” (Sensors)[7]. Survey of continuous/passive auth methods (biometric, behavior, context). Discusses security challenges (e.g. replay attacks) and privacy issues (constant sensing). Relevance: background on continuous authentication, illustrating trade-offs when using sensor/behavior data for ongoing user verification.
Wang et al. (2023) – “AU-ZTAC: Attribute and User Trust Score-Based Zero Trust Access Control in IoV” (Electronics)[8]. Proposes a Zero-Trust model that computes a user trust score from behavior and attributes, integrated with ABAC to decide access in vehicle networks. Experiments show the trust-based approach yields flexible, fine-grained control and enhances IoV security[8]. Relevance: examples of dynamic trust scoring (though IoV-focused) applicable to our trust-risk model.
Hu et al. (2023) – “N-Accesses” (Sensors)[9]. Blockchain-enabled access control for IoT data. Data owners host files off-chain; smart contracts govern n-times access tokens with deadlines using hash-chains. Key benefit: smart contracts enforce token usage limits and immutably log all accesses. Performance evaluation (via simulation) shows feasible overhead. Relevance: demonstrates blockchain + smart contracts for fine-grained, auditable access control.
Yaqub et al. (2024) – “Blockchain-enabled Policy-Based Access Control for EHR” (PeerJ CS)[10]. Access control for healthcare data: Subjects/controllers define policies, and smart contracts grant/revoke/check access per GDPR. Everyone (subject, controller, requester) can audit logs via blockchain. Shows blockchain empowers dynamic consent and transparent privacy enforcement. Relevance: example of integrating policy-based AC and immutable logging via blockchain in a regulated domain.
Tawfik et al. (2025) – “ACHealthChain” (Sci. Reports)[11]. Hyperledger Fabric + IPFS framework for healthcare data sharing. Introduces PolicyChain (fine-grained policy and revocation) and LogChain (audit trail). Patient data is sharded into EHR and diagnosis chains. Experiments: 19.7% throughput gain and 87% latency reduction vs. baseline. Relevance: a high-performance permissioned-blockchain AC system with multi-chain logging.
Zisad (2026) – “LLMAC: A Global and Explainable Access Control Framework with LLM” (arXiv)[12]. Introduces LLMAC, an LLM-based model that unifies RBAC, ABAC, and DAC. Trained on synthetic policy scenarios, it achieves 98.5% accuracy (vs 14–58% for individual models) and generates human-readable explanations for each decision[12]. Relevance: shows potential of AI (LLMs) to interpret and explain complex access policies.

DESIGN FLOW/PROCESS

3.1 Concept Generation
Currently, most systems use static authentication mechanisms, meaning that every user must go through the same login process regardless of their identity, behaviour, or context. Typically, this involves entering a username and password, and an additional verification step such as a one-time password (OTP). These methods treat all users equally, without considering whether the login attempt is coming from a trusted device, a familiar location, or a suspicious environment.
However, this uniform approach presents significant security limitations. Static authentication systems are unable to adapt to changing user behaviour or detect anomalies effectively. For example, if an attacker gains access to valid credentials, the system cannot distinguish between a legitimate user and a malicious actor. Similarly, insider threats, where authorized users misuse their access privileges, are difficult to detect because the system inherently trusts authenticated users without evaluating their intent or behaviour.
Moreover, static systems ignore important contextual factors such as login time, geographic location, device information, and historical usage patterns. A login attempt at an unusual hour or from an unknown device is treated the same as a routine login, which increases vulnerability to unauthorized access. As a result, these systems lack the flexibility and intelligence required to handle modern security challenges. Therefore, there is a growing need for dynamic and adaptive authentication mechanisms that can evaluate user risk in real time and adjust security measures accordingly. Such systems can significantly enhance security by incorporating behavioural analysis, contextual awareness, and intelligent decision-making into the authentication process.

3.2.2 Blockchain-Based Audit and Trust Mechanism
Need for Blockchain in the Proposed System
In traditional systems, logs and audit records are typically stored in centralized databases such as SQL or NoSQL systems. While these systems are efficient, they suffer from critical security limitations such as unauthorized modification of logs, deletion of audit records, and lack of traceability. The data stored in such databases can be modified, deleted, or tampered by administrators or attackers who gain sufficient privileges. This creates a major issue in security-sensitive environments where trust, accountability, and traceability are essential.
For example, if a malicious user gains administrative access, they can alter login records or delete traces of unauthorized access. This makes it difficult to detect breaches and perform forensic analysis.
To overcome it, the proposed system integrates a blockchain-based audit mechanism, which ensures that all critical system events are recorded in a secure and tamper-proof manner.
Blockchain is a distributed ledger technology where data is stored in the form of blocks, and each block is linked to the previous one using cryptographic hashes. This creates a chain-like structure where altering any previous record would require changing all subsequent blocks, which is computationally infeasible.
In this system, blockchain is used not for cryptocurrency, but for secure logging, event tracking, trust establishment 
Key Properties Utilized
Immutability: Once a record is written to the blockchain, it cannot be modified or deleted. This means login records are permanent, access decisions cannot be altered, and full audit history is preserved 
Transparency: All authorized participants can view the recorded transactions. Means admins can verify actions, Stakeholders can audit decisions and there will no hidden modifications 
Decentralization: Data is not stored in a single location but distributed across nodes. Thus, there is no single point of failure, and no single authority can manipulate data.
Cryptographic Security: Each block is secured using hashing algorithms. This guarantees data integrity and any tampering is instantly detectable. 

What Data on Blockchain: The system logs only critical events, not entire datasets (to optimize performance and cost).

3.3 Design Constraints
The proposed AI-driven authentication and authorization system operates under several critical design constraints that influence its technical architecture, scalability, and real-world applicability. These constraints are not only technical but also legal, economic, and societal in nature, requiring a balanced and well-informed design approach.
Regulatory and Privacy Constraints:
One of the most significant constraints is compliance with data protection regulations such as the General Data Protection Regulation (GDPR) and similar frameworks. Since the system processes sensitive user data—including identity credentials, behavioral patterns, and access logs—it must ensure strict privacy protection. This introduces limitations on how data can be collected, stored, and analyzed. For example, continuous behavioral monitoring improves security but raises privacy concerns, requiring mechanisms such as user consent, anonymization, and encryption. Additionally, features like the right to access and delete data must be incorporated, which impacts database design and storage strategies.

Economic and Resource Constraints:
The integration of blockchain and machine learning introduces both computational and financial overhead. Blockchain systems, particularly public ones, can incur transaction costs and scalability limitations, while private blockchains require dedicated infrastructure and maintenance. Similarly, machine learning models require substantial computational resources for training and periodic updates. This creates a trade-off between model complexity and system efficiency. A highly accurate but resource-intensive model may not be practical for real-time authentication systems, necessitating the use of optimized or lightweight models that balance performance with cost.

Environmental Constraints:
Energy consumption is an important consideration, especially when combining blockchain and machine learning technologies. Energy-intensive consensus mechanisms and large-scale model training can increase the system’s environmental footprint. Therefore, the design must prioritize efficiency by adopting lightweight blockchain mechanisms and minimizing unnecessary computations. This constraint indirectly affects architectural decisions, such as choosing permissioned blockchains and limiting the frequency of model retraining.
Fairness, Safety, and Ethical Constraints:
The use of AI for risk-based authentication introduces the challenge of ensuring fairness and avoiding bias. If the model is trained on imbalanced or non-representative data, it may produce biased risk scores, leading to unfair access denial or inconsistent behavior. This is particularly critical in security systems where decisions directly impact user access. To address this, the system must include mechanisms for bias detection, model validation, and explainability. Additionally, incorporating a human-in-the-loop approach for sensitive decisions can improve reliability and reduce the risk of incorrect automated actions.

Implementation Feasibility Constraints:
The system must be practically implementable using available technologies and within project limitations. The chosen stack—Python for machine learning, Flask or FastAPI for backend services, MongoDB for data storage, and a lightweight blockchain framework such as Hyperledger—supports modular and scalable development. However, integrating these components introduces complexity in terms of system coordination, latency, and data consistency. Ensuring seamless interaction between the ML model, backend APIs, and blockchain layer is a key design challenge that must be addressed through efficient system architecture.

Social and Political Constraints:
Finally, user trust and regulatory policies significantly influence system adoption. Users may be hesitant to rely on AI-driven decisions, particularly when they lack transparency. Therefore, the system must provide clear explanations for its decisions and maintain transparency in data usage. At the same time, political and legal requirements such as data sovereignty impose restrictions on where and how data can be stored and processed. These constraints require the system to be adaptable to regional regulations while maintaining consistent functionality.

3.4 Alternative Designs
To design a robust AI-driven authentication and authorization system, two alternative architectures were explored. These designs differ fundamentally in how decisions are made, how uncertainty is handled, and how system components interact under real-world constraints such as latency, scalability, and trust.

3.4.1 Design 1: Fully Automated AI-Based System
End-to-End Decision Pipeline:
In this architecture, the authentication process is entirely driven by a machine learning inference pipeline. When a user initiates a request, the backend system captures multiple real-time features such as IP address, device fingerprint, login timestamp, geolocation, and behavioral patterns (e.g., typing speed or access frequency). These features are normalized and passed into a trained ML model, which computes a probability-based risk score. A decision engine applies threshold logic (e.g., allow if score < 0.3, deny if > 0.7, else trigger MFA), and the response is returned instantly. This pipeline operates synchronously, ensuring low latency and high throughput. 

System Architecture and Component Interaction:
The backend (Flask/Fast API) acts as the orchestration layer, integrating the feature extractor, ML inference engine, and decision module. 
The ML model can be deployed as an embedded model (loaded in memory for fast inference) or A separate microservice (for scalability and independent updates).MongoDB is used for storing structured and semi-structured data such as login history, risk scores, and user metadata. 
Optionally, a blockchain layer can be integrated to store hashed logs of authentication decisions, ensuring immutability and auditability. The system follows a stateless API design for scalability.


Model Behaviour and Optimization Considerations:
The effectiveness of this design heavily depends on the quality of the ML model. Feature engineering plays a critical role, including:
Temporal features (login time deviation)
Spatial features (location anomaly detection)
Device consistency (new vs known device)
The model must be periodically retrained using updated datasets to adapt to evolving user behaviour. However, increasing model complexity (e.g., deep learning) may introduce latency, so a trade-off between accuracy and response time must be carefully managed.

Advantages in Large-Scale Systems:
This design is highly scalable due to its fully automated nature. It supports real-time decision-making, making it suitable for applications such as large SaaS platforms or APIs where thousands of requests per second must be handled. The absence of human intervention reduces operational costs and ensures consistent decision logic across all users.

Limitations and System Risks:
The primary limitation lies in the lack of a verification layer for uncertain predictions. ML models are inherently probabilistic and may fail in edge cases or unseen scenarios. False positives (legitimate users denied) and false negatives (malicious access allowed) can directly impact system security and user experience. Additionally, the black-box nature of some models reduces explainability, making it difficult to justify decisions in critical environments.

3.4.2 Design 2: Hybrid AI + Voting-Based System (Proposed)
Multi-Layer Decision Pipeline:
This architecture introduces a layered decision-making process that combines AI efficiency with human intelligence. The initial stages are identical to the automated system: feature extraction, ML-based risk scoring, and threshold evaluation. However, instead of forcing a binary decision for all cases, the system introduces a third “uncertain” zone. Requests falling into this zone are escalated to a voting-based validation layer. This creates a three-tier pipeline:
Low risk → Auto approval
High-risk → Auto rejection or strict verification
Medium-risk → Human-assisted decision

Detailed Voting Mechanism and Consensus Logic:
The voting module is implemented as a separate service integrated with the backend. When triggered, it sends structured request data to a set of authorized reviewers (admins or trusted users). Each reviewer is provided with:
Risk score and anomaly indicators
Historical behaviours summary
Contextual metadata (device/location mismatch, unusual activity)Reviewers cast their decision via a dashboard interface. The system applies a consensus algorithm such as majority voting or weighted voting (e.g., admin votes carry more weight). Timeout mechanisms are implemented to handle delays, after which fallback rules (e.g., deny or escalate further) are applied.

System Integration and Data Flow:
The backend coordinates between multiple modules:
ML inference engine
Decision engine
Voting service
Notification system (email/web alerts)
MongoDB stores detailed logs including risk scores, voting results, and final decisions. A lightweight blockchain (e.g., Hyperledger) records hashes of votes and outcomes, ensuring tamper-proof auditing. This layered architecture introduces asynchronous components, especially in the voting phase, which must be managed carefully to avoid bottlenecks.

Reliability, Fairness, and Explainability Enhancements:
By incorporating human validation, the system significantly improves decision reliability in ambiguous cases. It reduces the impact of model bias and provides a mechanism for explaining decisions, as human reviewers can justify their choices. This is particularly important in enterprise or high-security environments where accountability is required. The system can also use voting outcomes as feedback data to retrain and improve the ML model over time (active learning loop).

Trade-offs and System Complexity:
The major trade-off is increased system complexity and latency. Implementing a voting mechanism requires additional components such as user interfaces, notification systems, and consensus logic. The response time for medium-risk requests depends on human participation, which may not always be immediate. Scalability is also partially constrained by the availability of reviewers. However, these trade-offs are acceptable in systems where correctness, transparency, and security are prioritized over speed.

Comparative Technical Insight
Decision Strategy:
Fully automated systems rely entirely on probabilistic ML decisions, whereas hybrid systems introduce deterministic human validation for uncertain cases.
Latency vs Accuracy Trade-off:
Automated systems achieve low latency but may compromise accuracy in edge cases. Hybrid systems increase latency slightly but significantly improve reliability and correctness.
System Complexity:
The automated design is simpler with fewer components, while the hybrid design involves multiple interacting modules, requiring careful orchestration and synchronization.
Adaptability and Learning:
Hybrid systems provide continuous feedback through voting outcomes, enabling better model retraining and long-term performance improvement.



Conclusion
While the fully automated AI system is efficient and scalable, it lacks robustness in handling uncertain or high-risk scenarios. The hybrid AI + voting-based system introduces a more balanced approach by combining machine intelligence with human judgment. Despite higher complexity and latency, it offers superior accuracy, transparency, and trust, making it more suitable for real-world deployment in sensitive authentication environments.

3.5 Best Design Selection
After evaluating the alternative system architectures, the Hybrid AI + Voting-Based System is selected as the most suitable design for the proposed authentication and authorization framework. This decision is based on a comprehensive analysis of performance, reliability, scalability, and real-world applicability.

Balanced Decision-Making (Automation + Human Intelligence):
The hybrid model effectively combines the speed of machine learning with the contextual understanding of human reviewers. While the AI model handles most of the low-risk and high-risk decisions automatically, uncertain cases are escalated to a human validation layer. This layered approach ensures that decisions are not solely dependent on probabilistic outputs of the ML model, thereby improving overall system robustness. It introduces a controlled decision pipeline where automation is used for efficiency and human input is used for critical judgment.

Reduction of False Positives and False Negatives:
In fully automated systems, incorrect predictions (false positives and false negatives) can significantly impact both security and user experience. The hybrid approach mitigates this issue by introducing a verification mechanism for medium-risk cases. Human reviewers can analyze contextual anomalies (e.g., unusual login location but valid reason) and override incorrect AI predictions. This reduces the likelihood of denying legitimate users or allowing malicious access, thereby increasing the accuracy and reliability of the system.

Adaptive Risk-Based Authentication Mechanism:
The system dynamically classifies authentication requests into low, medium, and high-risk categories based on real-time ML inference. This enables risk-adaptive access control, where different levels of security measures are applied depending on the context. For example:
Low risk → Immediate access
Medium risk → Human validation
High-risk → Denial or strict verification
This adaptive mechanism ensures efficient resource utilization while maintaining high security standards.

Improved Transparency and Explainability:
One of the major limitations of AI-based systems is the lack of explainability. The hybrid model addresses this by incorporating human decisions in the loop, making the system more transparent. Each decision, especially in medium-risk cases, can be justified through voting outcomes and reviewer feedback. Additionally, storing decisions and voting logs enables auditability, allowing administrators to trace how and why a particular decision was made.

Enterprise-Level Security and Practical Applicability:
In real-world enterprise environments, critical access decisions often require multi-level approval mechanisms. The hybrid model aligns with such practices by integrating a voting-based validation system. It supports role-based reviewers (e.g., administrators, managers) and can be extended to include policy-based approvals. This makes the system highly suitable for enterprise Identity and Access Management (IAM) scenarios, where both security and accountability are essential.

Integration with Blockchain for Audit and Integrity:
The hybrid system can leverage a lightweight blockchain to store hashes of decisions and voting records. This ensures that all critical actions are tamper-proof and verifiable. Unlike the fully automated system, where logs may be altered, the blockchain layer in the hybrid design enhances trust and integrity by providing an immutable audit trail.

Continuous Learning and Feedback Loop:
Another key advantage of the hybrid system is its ability to improve over time. The outcomes of human voting can be used as labeled data to retrain and refine the ML model. This creates a feedback loop where the system becomes more accurate as it learns from real-world decisions. Such adaptability is crucial for handling evolving user behavior and emerging security threats.


Trade-off Justification (Latency vs Reliability):
Although the hybrid system introduces additional latency for medium-risk cases due to human involvement, this trade-off is justified by the significant improvement in decision accuracy and trustworthiness. In security-critical systems, correctness and reliability are more important than minimal response time. Therefore, the slight delay is acceptable in exchange for enhanced system integrity.

Conclusion
The Hybrid AI + Voting-Based System provides an optimal balance between efficiency, accuracy, and trust. By integrating automated intelligence with human validation and secure audit mechanisms, it addresses the key limitations of fully automated systems. Hence, it is selected as the final design for the proposed AI-driven authentication and authorization system.

3.6 System Architecture Overview
The proposed system follows a modular and layered architecture, where each component is responsible for a specific function in the authentication and authorization pipeline. This design ensures scalability, maintainability, and clear separation of concerns. The system integrates machine learning, backend services, database storage, blockchain logging, and human validation into a unified workflow.

1. User Module
The User Module acts as the entry point of the system, where users initiate authentication requests through a web or application interface.
It captures user credentials (username/password or token) along with contextual data such as device information, IP address, and session details (mentioned above)
This module is responsible for securely transmitting request data to the backend API using encrypted communication (HTTPS).
It also displays responses such as access granted, denied, or additional verification requests (e.g., voting or MFA).




2. Authentication Engine (ML Model)
This component serves as the core intelligence layer of the system.
It uses a trained machine learning model (e.g., Random Forest, Logistic Regression, or Neural Network) to evaluate incoming requests.
The engine processes extracted features such as login frequency, device consistency, and location anomalies to generate a risk score.
It operates in real-time and is optimized for fast inference, ensuring minimal delay during authentication.

3. Risk Analyzer
The Risk Analyzer interprets the output of the ML model and classifies the request into predefined categories: low, medium, or high risk.
It applies threshold-based logic and may include dynamic adjustments based on system behaviour or historical trends.
This component acts as a decision pre-processor, determining whether the request should be automatically handled or escalated.
It plays a critical role in enabling risk-adaptive authentication, improving both security and efficiency.

4. Blockchain Logger
The Blockchain Logger is responsible for maintaining a tamper-proof audit trail of critical system events.
It stores hashed records of authentication decisions, voting outcomes, timestamps, and user actions.
A lightweight or permissioned blockchain (e.g., Hyperledger) is used to ensure low latency and controlled access.
This component enhances transparency, integrity, and accountability, making the system suitable for compliance and forensic analysis.

5. Access Control Engine
The Access Control Engine enforces the final decision based on inputs from the Risk Analyzer and Voting System.
It implements policies such as:
Allow access
Deny access
Trigger multi-factor authentication (MFA)
It integrates with role-based access control (RBAC) or attribute-based access control (ABAC) models to ensure that users receive appropriate permissions.
This module acts as the execution layer, converting decisions into actual system actions.

6. Voting System
The Voting System is activated for medium-risk or uncertain cases, introducing human validation into the process.
It notifies authorized reviewers (e.g., admins or trusted users) through a dashboard or alert mechanism.
Reviewers analyse contextual information and cast votes (approve/deny), which are processed using a consensus algorithm (e.g., majority voting).
This module enhances decision reliability, fairness, and explainability, reducing dependency on purely automated decisions.

7. Database (MongoDB)
The database acts as the central storage layer of the system.
It stores:
User profiles and credentials
Authentication logs and risk scores
Voting records and outcomes
MongoDB is chosen due to its flexibility in handling semi-structured data and scalability for large datasets.
The stored data is also used for model retraining and analytics, enabling continuous system improvement.

ML model generates risk score
Risk Analyzer classifies request
Low/High risk → handled automatically
Medium risk → forwarded to Voting System
Final decision enforced by Access Control Engine
Logs stored in Database and Blockchain

The architecture ensures a balanced integration of automation, human validation, and secure logging. By dividing the system into modular components, it achieves scalability, flexibility, and robustness, making it suitable for real-world Identity and Access Management (IAM) applications.

3.7 Design Flow (Algorithm)
The proposed system follows a structured algorithm that integrates machine learning-based risk evaluation with rule-based decision-making and human validation. The workflow is divided into two major phases: authentication phase and authorization (resource access) phase.

Step-by-Step Algorithm
Step 1: User Authentication Request Initiation
The process begins when a user submits a login request through the system interface. The request includes credentials and contextual information such as device ID, IP address, and session metadata.
Step 2: Fetch User Data and Context
The system retrieves stored user information from the database, including historical login patterns, previous access logs, and behavioural data required for risk analysis.
Step 3: ML-Based Risk Score Calculation
The extracted features are passed to the machine learning model, which computes a risk score representing the likelihood of suspicious or anomalous behaviour.
Step 4: Risk Categorization
The Risk Analyzer classifies the request into one of three categories Low, Medium and High Risk
Step 5: Low-Risk Handling
If the request is classified as low risk:
Access is immediately granted
The authentication event is securely logged to the blockchain for audit purposes
Step 6: Medium-Risk Handling
If the request falls under medium risk:
Additional authentication mechanisms are applied (e.g., OTP, secondary verification)
The event is logged in the system for monitoring and future analysis
Step 7: High-Risk Handling
If the request is identified as high risk:
Access is restricted or denied
The system may trigger alerts or continuous monitoring for potential threats

Authorization Phase (File/Resource Access)
Step 8: Resource Access Request
After successful authentication, the user requests access to a protected resource (e.g., file or system service).
Step 9: AI-Based Validation of Request Context
The system analyses the request reason using AI techniques (e.g., NLP or rule-based validation) to determine whether the access request is legitimate.
Step 10: Low-Risk and Valid Request Handling
If the request is valid and associated with low-risk Access to the requested resource is granted immediately
Step 11: Medium/High Risk Evaluation
If the request is categorized as medium or high risk: The system evaluates whether the risk exceeds a predefined threshold
Step 12: Voting System Trigger
If the threshold is exceeded, then the request is escalated to the voting system for human validation
Step 13: Vote Collection Process
Authorized reviewers analyse the request details and cast their votes (approve/deny) through the system interface.
Step 14: Consensus-Based Decision Making
The final decision is determined using a consensus mechanism (e.g., majority voting), ensuring fairness and reliability.
Step 15: Secure Logging and Audit
All actions, including risk scores, decisions, and voting results, are recorded in the blockchain to ensure immutability, transparency, and auditability.

Conclusion
The algorithm ensures a multi-layered decision-making process that combines AI-based risk assessment, rule-based control, and human validation. This design enhances security, reduces incorrect decisions, and provides a transparent and auditable authentication and authorization framework.

Phase 3: Blockchain Integration
Objective
The main objective of this phase is to implement a secure and tamper-proof logging mechanism for all authentication and authorization events. 
Unlike traditional systems where logs can be modified or deleted, blockchain ensures that once data is recorded, it remains immutable and verifiable. 
This helps in maintaining data integrity, transparency, and trust, which is crucial for sensitive systems like identity and access management. 

Implementation Details
1. Event Capture
The system records all critical activities such as login attempts, ML-based risk decisions, and authorization outcomes. 
Each event is structured with important details including user ID, timestamp, IP address, device information, and decision result. 
This structured format ensures consistency and makes further processing easier. 

2. Hash Generation (SHA-256)
Each captured event is converted into a hash using the SHA-256 algorithm, creating a unique digital fingerprint. 
Even a small change in the input data produces a completely different hash, making it highly secure. 
This ensures that any tampering with stored data can be easily detected. 

3. Block Creation
After hashing, the event is stored inside a block along with its hash and the hash of the previous block. 
This linking of blocks forms a chain, where each block depends on the previous one. 
If any block is altered, the entire chain becomes invalid, ensuring strong data protection. 

4. Blockchain Storage
The blocks are stored in a private blockchain network, which restricts access to authorized users only. 
This approach provides better control, security, and performance compared to public blockchains. 
The distributed ledger ensures that multiple nodes maintain copies of the data, preventing single points of failure. 

5. Backend Integration
The blockchain system is integrated with the backend so that every event is automatically recorded in real-time. 
When a login or decision event occurs, the backend generates the hash, creates a block, and appends it to the blockchain. 
This process is seamless and does not affect the system’s performance. 

6. Integrity Verification
The system includes a verification mechanism that recalculates hashes and checks block linkage. 
If any mismatch is detected, it indicates possible tampering or unauthorized modification. 
This ensures continuous monitoring of data integrity and strengthens system security. 

Tools & Technologies Used
Blockchain Framework: Hyperledger Fabric or custom lightweight blockchain 
Hashing Algorithm: SHA-256 
Backend Integration: Python / Node.js 
Ledger Type: Private Distributed Ledger 

Output
The final output is a secure and immutable audit logging system that records all authentication events. 
It ensures that logs cannot be modified or deleted, providing trustworthy and transparent records. 
This system supports auditing, forensic analysis, and compliance with security standards.

When the system detects a medium or high-risk request, it automatically triggers the voting process. 
APIs are developed to initiate voting sessions and notify eligible reviewers. 
The request details (user, reason, risk score, context) are sent to reviewers for evaluation. 

2. Role-Based Reviewer Access
Only authorized users such as admins or trusted reviewers are allowed to participate in voting. 
Role-based access control (RBAC) ensures that only qualified individuals can approve or reject requests. 
This prevents unauthorized decision-making and maintains system security. 

3. Vote Collection and Storage
Reviewers submit their decisions (approve/reject) through APIs or a dashboard interface. 
Each vote is securely stored in the database along with reviewer identity and timestamp. 
This ensures transparency and allows tracking of decision history. 

4. Consensus Mechanism (Majority Voting)
The system applies a majority voting algorithm to determine the final outcome. 
If most reviewers approve, access is granted; otherwise, it is denied. 
This reduces bias and ensures that decisions are not dependent on a single individual. 

5. Dashboard Interface
A user-friendly dashboard is developed where reviewers can view pending requests and cast their votes. 
The interface displays important details such as user information, risk score, and reason for access. 
This improves usability and enables quick, informed decision-making. 

6. Backend Integration
The voting system is integrated with the main authentication workflow.
Once voting is completed, the final decision is sent back to the system for execution. 
The result is also logged (and can be stored in blockchain for immutability).

Frontend (optional): React.js or HTML/CSS for dashboard interface

Testing Tools: Postman for API testing and validation 

Output
The output of this phase is a functional voting-based authorization system that enables secure and reliable decision-making. 
It ensures that uncertain access requests are validated through multiple reviewers, improving both accuracy and accountability. 
This system enhances overall security by combining automated intelligence with human verification. 

Phase 5: AI-Based Request Validation
Objective
The objective of this phase is to validate the user-provided reasons when requesting access to sensitive resources.

By incorporating AI-based validation, the system ensures context-aware authorization, improving both security and decision accuracy.

CONCLUSION AND FUTURE WORK

5.1 Conclusion
The primary objective of this project was to design and implement an intelligent authentication system that enhances traditional login mechanisms by incorporating machine learning-driven risk assessment. Conventional authentication systems rely heavily on static credentials such as usernames and passwords, which are vulnerable to attacks like credential stuffing, phishing, and brute-force attempts. To address these limitations, the proposed system introduces a dynamic and context-aware authentication mechanism.
The system leverages contextual features such as IP address, login time, device information, and behavioural patterns to evaluate the legitimacy of each login attempt. These features are processed through a machine learning model trained to classify login attempts as either legitimate or suspicious. Based on the predicted risk score, a decision engine determines the appropriate authentication response, such as allowing access, triggering additional verification, or denying the request.
One of the key strengths of the system is its modular architecture, which integrates multiple components including:
Feature Extraction Module for capturing contextual login data 
Machine Learning Model for risk prediction 
Decision Engine for access control enforcement 
Blockchain-based Logging System for secure and tamper-proof audit trails 

The results demonstrate that the system achieves a high level of effectiveness in detecting anomalous login attempts, with an accuracy ranging between 85% and 92%. This indicates that machine learning can significantly enhance authentication systems by introducing adaptive and intelligent decision-making capabilities.
Furthermore, the system maintains a balance between security and usability. Instead of enforcing strict multi-factor authentication (MFA) for all users, it applies additional verification only when a login is classified as high-risk. This selective enforcement improves user experience while maintaining strong security controls.
In conclusion, the project successfully validates the concept of risk-based authentication (RBA) integrated with machine learning and secure logging. It provides a scalable and extensible framework that can be further enhanced for real-world deployment in identity and access management (IAM) systems.

5.2 Deviation from Expected Results
While the system achieved its core objectives, several deviations from the expected results were observed during implementation and testing. These deviations highlight practical challenges and limitations that must be addressed in future iterations.

Model Accuracy Limitations
Although the model achieved an accuracy of 85–92%, it fell short of the expected benchmark of above 95%. This limitation can be attributed to:
Use of synthetic or limited datasets, which do not fully represent real-world login behavior 
Lack of sufficient anomalous data samples for training 
Simpler models such as Logistic Regression and Random Forest, which may not capture complex temporal patterns 
As a result, the model’s predictive capability is somewhat constrained in highly dynamic environments.

5.2.2 False Positives and False Negatives
The system exhibited both:
False Positives: Legitimate users flagged as suspicious 
False Negatives: Malicious attempts classified as safe 
False positives were more prominent when users logged in from:
New devices 
Different geographic locations 
Unusual time patterns 
This indicates that the system lacks sufficient behavioral history and adaptability, which affects trust and usability.


Dataset Constraints
The dataset used for training lacked:
Real-world diversity (global IP variations, device fingerprints) 
Long-term behavioral tracking 
High-quality labeled attack data 
This limitation reduced the model’s ability to generalize across different user profiles and attack scenarios.

Latency in Real-Time Processing
The system introduced minor delays due to:
Feature extraction overhead 
Machine learning inference time 
Blockchain transaction processing 
Although acceptable in a prototype, such latency may become critical in large-scale production environments where thousands of authentication requests occur simultaneously.

Blockchain Overhead
While blockchain ensured:
Data integrity 
Tamper-proof logging 
Transparency 
It also introduced:
Increased computational cost 
Slower write operations 
Scalability concerns 
This trade-off between security and performance must be optimized.

Limited Behavioural Analysis
The current system primarily relies on static contextual features and lacks:
Continuous behavioural tracking 
Advanced user profiling 
Session-based anomaly detection 
This limits the system’s ability to detect sophisticated attacks such as session hijacking.
