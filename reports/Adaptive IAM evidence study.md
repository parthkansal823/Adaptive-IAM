# Adaptive IAM exposes authentication policy tradeoffs

Adaptive IAM now implements the supplied idea as a research system with contextual authentication, human-reviewed resource authorization, reusable website sign-in and a real local Solidity registry. Its clearest measured improvement is **lower probability error and lower legitimate-user friction**, accompanied by **lower suspicious-event detection**. The new experiment pipeline separates training, calibration, selection and testing, preserves rejected candidates, and reports conditional uncertainty. Website authentication uses a constrained OAuth/OIDC code flow, while permission remains a separate server-enforced decision. Docker isolates the API, console and development chain with restricted privileges and loopback-only published endpoints. These engineering artifacts make the idea executable and reviewable; synthetic labels, demo authentication factors and single-host chain administration still prevent claims of production effectiveness. This report and the [manuscript draft](../docs/paper/MANUSCRIPT.md) provide an evidence-backed starting point for a new paper, with authorship left for confirmation. ([Measured artifacts](../experiments/results.json), [Architecture](../docs/ARCHITECTURE.md), [Deployment](../deployment/README.md))

## Authentication and permission now have distinct authority

The system first authenticates an identity using password verification and explicit risk policy. Elevated risk produces a short-lived, single-use demo challenge; high risk blocks login. A verified identity can request a resource but cannot choose reviewer identities, vote weights or the final grant. Approval requires the resource owner, at least two eligible votes and a strict majority of all selected reviewer weight. The owner has a veto, and pending requests deny after 48 hours. LLM recommendations and text labels do not authorize access. These boundaries implement a resource-centered interpretation of NIST's separation between authentication and authorization. ([API contract](../docs/API.md), [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final))

A website administrator registers an exact callback, scopes and resource allowlist. The relying-party server redirects to Adaptive IAM, binds the transaction to state, nonce and S256 PKCE, then verifies an RS256 ID token and matching subject. Application access tokens remain on the website server and have no console voting authority. Every protected response checks a live subject/client/resource-bound grant. OIDC supplies identity semantics alongside OAuth's access flow; a successful login or consent screen does not itself create a resource grant. The Node and Python examples demonstrate this sequence, rather than adding authentication to websites the developer does not control. ([Website integration](../docs/INTEGRATION.md), [PKCE](https://www.rfc-editor.org/info/rfc7636/), [OAuth security BCP](https://www.rfc-editor.org/info/rfc9700/), [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html))

## Calibration lowers error while detection also falls

The main risk experiment generates **10,000 synthetic events**, using seed 20261009 and a 6,000/1,000/1,000/2,000 train/calibration/selection/test split. The paper-inspired score blends logistic regression and random forest with weights 0.4/0.6. An interaction candidate is rejected on validation; sigmoid calibration is retained after reducing selection-set Brier loss. The binary classification threshold and authentication challenge threshold are selected separately before test evaluation. ([Protocol and results](../experiments/results.json))

Held-out accuracy rises from **74.90% to 81.50%**, F1 from 0.4716 to 0.4832, and Brier loss falls from **0.1747 to 0.1165**. Ranking remains unchanged at ROC-AUC 0.7743, while classification suspicious recall falls from 64.00% to 49.43%. An always-legitimate classifier scores 82.50% accuracy with zero suspicious recall, demonstrating why accuracy cannot carry the security argument. Brier loss also combines reliability and discrimination; it should be interpreted with the unchanged ranking and a future reliability analysis, rather than equated with calibration quality alone. ([Results](../experiments/results.json), [Calibration documentation](https://scikit-learn.org/stable/modules/calibration.html))

At the actual authentication operating point, suspicious challenge/block recall falls from **86.86% to 84.00%** and direct suspicious allowance rises from 13.14% to 16.00%. Legitimate friction falls from **56.48% to 51.45%**. The candidate's low threshold is approximately 0.10533, selected to achieve at least 80% suspicious detection on validation, with high threshold 0.7. Keeping the original 0.3/0.7 cutoffs after calibration would reduce detection to **41.14%**, so that ablation is recorded and rejected. The research contribution is an explicit security/usability tradeoff and a reproducible policy failure analysis. ([Policy evidence](../experiments/results.json))

## Fresh seeds expose the limit of a validation target

The paired, class-stratified event bootstrap uses 1,000 replicates with a frozen model. Its F1 difference is +0.01166 with a 95% percentile interval **[-0.01784, +0.04121]**, which crosses zero. Brier loss decreases by 0.05813 and legitimate friction by 5.03 percentage points, while policy detection decreases by 2.86 percentage points; their conditional intervals preserve those directions. Five further 2,000-event batches use new seeds without retraining. These estimates describe one trained model and the simulator, with no multiplicity adjustment or real-population inference. ([Robustness results](../experiments/robustness.json))

![Paired bootstrap uncertainty](../experiments/figures/paired-uncertainty.png)

Figure: paired conditional differences; lower values favor Brier loss and friction, while higher values favor F1 and detection. [Vector export](../experiments/figures/paired-uncertainty.svg).

The independent candidate study generates another **12,000 events** with seed 20261509. Selection compares calibrated original blend, interaction logistic regression and histogram gradient boosting using validation Brier, ranking and detection/friction constraints. Validation retains the original calibrated blend; no runtime replacement occurs. On its new 2,400-event test partition, policy detection is **78.47%**, below the 80% validation target. This result shows that a selection target is not a held-out guarantee. It does not justify choosing a different model retrospectively from the test scores. ([Candidate-study protocol and all candidates](../experiments/candidate-study.json))

The text study preserves an original baseline with **60.25% accuracy and 0.625% suspicious recall**. Exploratory reanalysis tunes its Naive Bayes threshold on validation to 0.16, raising test accuracy to **81%**, suspicious recall to **52.5%** and F1 to 0.688525. These test template groups were already reported, so this is not a new untouched language evaluation. A word/character logistic candidate has perfect scores on that tiny test sample but is rejected because validation macro F1 is lower and it flags 50% of legitimate validation texts. Runtime support-based abstention and handwritten flags are excluded from the binary scores. Optional BERT and Ollama benefits remain unmeasured; LLMAC's author-reported synthetic-policy result belongs to a different system and task. Mandatory human review preserves the authority boundary. ([Text results and rejected candidate](../experiments/results.json), [LLMAC primary paper](https://arxiv.org/abs/2602.09392))

The separately frozen runtime diagnostic contains **32 manually authored cases**, including prompt injection, negation, quoted threats and Hindi/Hinglish. Runtime labels flag 12 of 16 author-suspicious cases and 2 of 16 author-benign cases; seven cases abstain as uncertain, giving **78.125% definitive coverage**. These are author expectations rather than verified attack truth, and their outcomes do not retune the model. The lexical negation rule is a bounded heuristic, not general language understanding. ([Case study](../experiments/case-study.json))

## Real local EVM execution retains local administrator trust

The Solidity registry executes on Ganache chain 31337, with a trusted writer recording audit checkpoints and hashed identity/resource grants. The backend uses a retryable outbox: local approval and a confirmed transaction are distinct states. A grant is mirrored only after its creation event is anchored and its owner/quorum still validates. Protected console access and website permission checks require both local authority and live contract authority when Web3 is enabled. Outage, expiry, revocation and checkpoint mismatch deny access. This is actual EVM behavior rather than calling a SQLite hash chain a blockchain. ([Contract](../blockchain/contracts/AccessGrantRegistry.sol), [Adapter](../backend/app/blockchain.py), [Ethereum contract semantics](https://ethereum.org/developers/docs/smart-contracts/))

An isolated Linux Docker run passes **11 Python blockchain tests and two grouped EVM tests**. Live cases include chain rollback, contract expiry despite an active SQLite record, a complete database hash rewrite that defeats local-only verification, fabricated grants without owner quorum and actual OIDC outage/revocation denial. They validate these local failure states while leaving throughput and independently administered consensus unmeasured. ([Boundary/live-RPC tests](../backend/tests/test_blockchain.py), [Contract tests](../blockchain/tests/contract.test.mjs), [Isolated environment](../deployment/compose.web3-tests.yaml))

A live Docker sign-in smoke flow also verifies confidential-client PKCE, signed RS256 identity with nonce/audience/issuer checks, human approval, a confirmed contract grant, revocation and client disable. The complete project verifier passes SDK, provider, history-feature and contract checks plus the frontend build. These are local functional checks; production interoperability and OIDC certification remain unestablished. ([Verification runner](../scripts/verify.py), [Integration guide](../docs/INTEGRATION.md))

Docker publishes the console/API and optional connected website only on host loopback, keeps RPC inside an internal bridge and uses non-root containers, read-only root filesystems, dropped capabilities and resource limits. Web services also join an edge bridge, which permits their outbound traffic. Persistent volumes retain registry, IAM and signing state. Containers and a single development chain still share an administrative host; its administrator can reset the chain. Hashing known identities does not establish anonymity, and no raw credentials, tokens or justification text belong on-chain. Assess the deployment through actual receipts and failure tests rather than tamper-proof or decentralized labels. ([Compose configuration](../compose.yaml), [Deployment operations](../deployment/README.md), [Docker security boundary](https://docs.docker.com/engine/security/))

## Independent data is the next evidence gap

The creator's public RBA corpus is **synthesized data**, with artificial values and an explicit production-use caution. The project supplies an optional chronological CSV adapter that computes features from prior events, records a digest and discloses unavailable signals. No completed external-data result is present in this evidence set. A new study needs independent provenance, verified takeover labels, temporal and user-disjoint cohorts, fixed operating-point comparisons and repeated retraining. The Wiefling study motivates historical and service-specific evaluation; its findings cannot be substituted for this prototype's outcomes. ([Creator dataset](https://github.com/das-group/rba-dataset), [Adapter](../scripts/evaluate_rba.py), [Author study](https://arxiv.org/html/2206.15139v2))

A submission should make the system's evidence boundaries part of its contribution: weak held-out text performance, a rejected calibration-policy combination, candidates rejected on validation, and detection regression after reduced friction. Independent incident labels, human text annotation, verified MFA, OIDC conformance and independently administered chain nodes would add the missing kinds of validity. Prespecifying those evaluations avoids turning exploratory test results into unearned improvement claims. ([Claim/evidence map](../research_notes/Adaptive%20IAM%20evidence%20study/gap-analysis.md))

## Conclusion

The most useful next research question is whether the lower-friction operating point survives independent telemetry while preserving a chosen detection budget. Keep that budget and the model-selection rule fixed before collecting the next test set. The existing prototype can then serve as a reproducible apparatus for evaluating the interaction between probabilistic risk, human authorization and verifiable grant enforcement, while a production identity system remains a separate engineering and validation objective.
